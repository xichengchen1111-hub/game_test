# 错日证词低配性能与可进入房屋扩展评估

2026 年 10 月 9 日。项目基线为 `aed8b2827f45525c3e04e766db1be9ed82005049`，Unity 6000.3.18f1。manifest 仍声明 URP 17.0.1，但 packages-lock 和本机实际加载包均为 17.3.0，本轮没有升级包。优先满足低配电脑流畅，同时为性能更强的电脑提供更好的画质。

可以继续制作精致模型和可进入房屋，并保留实体开关门、无黑屏进出和双向透明窗户。主要风险在于把所有房屋的完整陈设、灯光和人物同时保持最高成本。当前切片在开发电脑上有充足余量，但现有结构还不能据此承诺完整小镇在旧核显上流畅。建议同时建设画质档位、模型距离分级和房屋可见性管理。

## 当前项目的实际成本

通过 Unity Editor 打开现有 Town 场景读取资源，没有重新生成场景。统计包含镜头外物体，三角面数按场景实例累加，不能等同于每帧实际绘制数量。

| 项目 | 整个 Town | 钟表屋含老板 |
| --- | ---: | ---: |
| 渲染组件 Renderer | 489 | 201 |
| 材质槽位 | 533 | 201 |
| 不同材质 | 75 | 19 |
| 三角面 | 357,546 | 279,923 |
| Unity 导入后顶点 | 583,444 | 469,379 |
| 碰撞体 | 100 | 41 |
| 蒙皮人物渲染组件 | 2 | 1 |

钟表屋的 FBX 套件本身为 57 个 mesh、266,240 个三角面；57 个导出 mesh 不代表整座店只有 57 个渲染组件。原 Blender 顶点数也不能代替 Unity 导入顶点数，UV 和法线等边界会拆分顶点。老板模型只有 10,225 个三角面，当前主要几何成本在店内陈设，不需要为了优化改掉已经锁定的老板。

Town 有 14 盏实时灯，其中 1 盏方向光和 2 盏店内点光源投射软阴影；其余点光源没有阴影。当前没有 LODGroup，钟表屋模型也关闭了 Mesh LOD 自动生成；没有烘焙 lightmap，Town 的遮挡剔除数据为空。街面反射探针为 128px、OnAwake，不能把它误写成每帧重拍六个方向。

当前 PC 管线为 Forward+，启用 HDR、4× MSAA、全分辨率 SSAO、深度纹理和不透明颜色纹理；主阴影图 2048px、距离 55m、4 个级联，额外灯阴影图集 2048px。SRP Batcher 已启用，GPU Resident Drawer 未启用。Forward+ 的额外灯不能依靠“每物体 4 灯”这个序列化字段限制成本。[Unity Forward+ 规则](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/rendering/forward-rendering-paths.html) `Native RenderPass` 虽已勾选，当前 Windows 构建使用 D3D11，不能把它当作已获得 Vulkan、Metal 或 D3D12 对应收益的证据。[Unity URP 性能配置](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/configure-for-better-performance.html)

数据见 [Unity 资源统计](https://github.com/xichengchen1111-hub/game_test/blob/main/output/performance/2026-10-09/asset-audit.json)。其中全部 Art/Generated 贴图统计包含历史未使用资源，Editor 的资源内存估算也不等于 Player 显存占用。

## 独立 Player 测量

测试电脑为 Intel Core Ultra 9 285H、RTX 5060 Laptop GPU、约 32GB 内存，Windows D3D11，1920×1080 可见窗口。使用正常 release 构建，在独立测试包中临时启用 Frame Timing Stats，取消原有 60 帧上限和垂直同步以观察余量。每个固定视角预热 2 秒，连续采集三段各 5 秒；随后使用实际 CharacterController 做四次店门往返。测量期间没有截图。Frame Timing Stats 本身可能带来测量开销。[Unity 发布版本帧计时说明](https://docs.unity3d.com/6000.3/Documentation/Manual/frame-timing-manager-enable.html)

| 视角和配置 | GPU 中位耗时 | 整帧 P95 | 每帧绘制调用中位数 | 每帧提交三角面中位数 |
| --- | ---: | ---: | ---: | ---: |
| 当前配置 街上看店面 | 3.30ms | 3.91ms | 1,163 | 2,795,545 |
| 当前配置 透过橱窗看店内 | 3.59ms | 4.05ms | 857 | 2,422,227 |
| 当前配置 店内 | 4.01ms | 4.46ms | 665 | 2,329,751 |
| 试验低画质 店内 | 0.77ms | 2.75ms | 212 | 520,515 |
| 试验低画质 街上看店面 | 0.72ms | 2.82ms | 392 | 690,621 |

P95 表示 95% 的采样帧耗时不超过这个数。每帧三角面包含阴影、深度等重复提交，不能据此说店铺模型有两百多万面；场景静态几何较少，仍可能因多个 pass 获得较高的提交成本。

试验低画质同时关闭 HDR、SSAO、额外点光源阴影和不透明颜色纹理，MSAA 改为 1，主阴影改为 20m、1024px、1 级联，渲染比例改为 0.75。窗口和 UI 仍为 1920×1080，三维画面内部约为 1440×810。几何、门窗和可进入空间没有删减。这是多项设置组合对比，不能把约 81% 的店内 GPU 耗时下降归因于某一个开关，也不能宣称已经找到最佳低配画质。

四次实际进出店门和反复开关门共采集 7,385 帧，最长帧约 17.35ms，没有超过 33.33ms 的帧。这个短测没有在当前电脑上复现严重进屋卡顿；它不能排除慢磁盘、旧 CPU、首次资源加载或完整小镇中的停顿。门的动作通过交互组件调用，行走由程序控制，不是物理键鼠或陌生玩家测试。

Texture.currentTextureMemory 起始约 59.51MiB、结束约 60.51MiB；这项计数不包含全部渲染目标和内部图形资源，不能作为总显存或进程内存。短测也不足以判断长期探索是否泄漏。release 中未取得 GC Allocated In Frame 和独立 Render Thread 计数，汇总使用 null 表示缺失；采样器自身也会分配对象，不能把测量分配全部归因于游戏。

正常存档 SHA256 前后均为 `6DF4360A22901A5076831437CD721370F5DBE94CAF9F915DE57740A18E32E53A`。采样使用独立存档。正式游戏包、场景、画质配置和画质菜单均未被此次实验替换。[逐场景与逐次汇总](https://github.com/xichengchen1111-hub/game_test/blob/main/output/performance/2026-10-09/runtime-summary.json)

## 扩展后最需要控制的风险

| 优先级 | 当前依据与扩展影响 | 建议 |
| --- | --- | --- |
| 高 | 两盏有阴影点灯会为阴影捕获多个方向；复制到很多房间会显著增加提交和图形成本。当前组合对比已显示大幅减少 pass 的收益。 | 静态室内以烘焙照明为基础，人物使用光照探针；低档关闭额外实时阴影，高档给附近重要灯光有限配额。小零件不必全部投射实时阴影。 |
| 高 | 当前没有模型距离分级，钟表屋陈设占 Town 大部分几何；远处看不到的齿轮、表链和抽屉内部仍可能以完整几何参与渲染。 | 给建筑、柜台、钟表套件建立近中远级别；在不影响轮廓和证据可读性的距离简化小零件。优先优化陈设套件，保留锁定角色。 |
| 高 | Systems 加载 Town 后，当前室内常驻 Town，没有按区域卸载。只关闭 Renderer 不会自动释放模型和贴图。 | 先管理可见性和灯光，再根据真实内存压力引入房屋分块异步加载，不能只做画质菜单。 |
| 中高 | 街上看店面每帧 1,163 次绘制调用。增加独立物件、材质槽和阴影会给弱 CPU 带来更多提交工作。 | 共用材质和套件，按柜组或房间小区域组织几何；减少微小独立 Renderer。不要合成整个小镇或整栋超大 mesh，否则会损失剔除粒度。 |
| 中高 | 当前 PC 未启用贴图 mip 串流，所有被统计的美术贴图也未启用。独特房屋、人物和大贴图会增加常驻内存，核显还与系统共享内存。 | 建立每类资源的贴图上限和串流策略，保留证物、表盘和近景面部的清晰度。按 GPU 格式和 mip 层级计算成本，不按 PNG 文件大小估算。 |
| 中 | 透明窗、展柜和门玻璃会叠加像素工作；透过玻璃还会看到更多真实几何。当前 ClearGlass 只做简单颜色混合，没有场景折射采样。 | 保留透明玻璃，控制重复共面玻璃层和远处细物；低档不引入昂贵的折射效果。透明窗不能当实体遮挡墙处理。 |
| 中 | 钟表屋 FBX 保留 Read/Write，生成器也强制开启。对未来很多独特 mesh，会保留额外 CPU 数据并影响可采用的加载方式。 | 发布资源关闭不需要的 CPU 可读副本，几何验证留在 Editor；先检查碰撞、静态合批和运行时 mesh 访问需求，不能一律关闭。 |
| 中 | 新资源第一次可见时可能触发上传、shader 首次准备和大量组件激活。异步加载场景并不意味着所有工作都在后台。 | 玩家到门口前预加载，分批激活昂贵组件，预热实际会使用的 shader 组合；测首次进入与再次进入的差异。 |
| 中低 | 跨店铺边界及开门会同步序列化、写临时文件、复制再删除。当前短测没有严重停顿，慢磁盘或更大存档仍可能放大这项成本。 | 对连续状态变化做短时间合并，主线程生成纯数据快照，单一后台写入队列负责文件；保留退出刷盘、失败恢复和一致性。不要对每个物件开一条写盘线程。 |
| 中低 | 受保护的门每次交互最多做 25 次分配数组的 OverlapBox；运动中继续检查，并调用全局 Physics.SyncTransforms。 | 使用玩家层掩码、复用查询缓冲或直接针对玩家胶囊检测；批量同步变换，保留夹人保护。当前只有两扇此类门，不是已证明的主要瓶颈。 |
| 随规模提高 | 当前只有两套 Animator，但两个人物的生成器都设置 AlwaysAnimate 和 updateWhenOffscreen=true。未来增加很多人物、语音和行为逻辑后，画面外动画、寻路、音源和更新循环也会扩展。 | 远处人物降低更新频率并合理裁剪动画，保留逻辑状态；对白按需加载。现阶段不需要为两个人物引入复杂 ECS 系统。 |

点光阴影需要捕获六个方向，增加投影物也会增加成本；烘焙和限制额外灯阴影符合 Unity 的优化建议。[阴影优化](https://docs.unity3d.com/6000.3/Documentation/Manual/shadows-optimization.html)

Unity 的 LOD 可以减少多边形、材质复杂度以及 Renderer 数量；只改变 lodBias，不给资产建立实际分级，不会自动让现有模型变简单。[模型细节分级](https://docs.unity3d.com/6000.3/Documentation/Manual/LevelOfDetail.html)

SRP Batcher 减少状态准备成本，不能据它已启用就认定绘制调用已合并。手动合并 mesh 会损失独立剔除；动态合批也有 CPU 成本。当前已使用 Forward+，可把 GPU Resident Drawer 作为独立对比实验，它需要计算着色器支持并主要处理 MeshRenderer，不能代替人物动画和资源管理。[绘制调用优化选择](https://docs.unity3d.com/6000.3/Documentation/Manual/optimizing-draw-calls-choose-method.html)、[mesh 合批限制](https://docs.unity3d.com/6000.3/Documentation/Manual/DrawCallBatching.html)、[GPU Resident Drawer 条件](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/gpu-resident-drawer.html)

CPU 可读 mesh 会保留额外数据；关闭前需核对使用条件。符合条件的资源可以采用异步上传，不符合条件时仍可能同步上传。shader 第一次供驱动使用也可能引发停顿。[Mesh.isReadable](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Mesh-isReadable.html)、[资源上传](https://docs.unity3d.com/6000.3/Documentation/Manual/LoadingTextureandMeshData.html)、[shader 加载](https://docs.unity3d.com/6000.3/Documentation/Manual/shader-loading.html)

## 无黑屏进屋与透明窗的扩展方式

建筑保持一份共用布局、相同世界坐标和真实门窗。建筑外壳、实体门、透明玻璃和必要碰撞常驻附近；室内陈设可以按距离与可见性逐层启用。站在窗外能看见的桌椅和陈列必须保留，可以显示同一空间对应的简化版本。玩家靠近窗户或门口时，提前补齐完整陈设、人物和交互。

窗口可见性必须参与判断。不能简单地把“玩家还在屋外”当成隐藏全部室内的条件；也不能把关闭的玻璃门当成不透明遮挡。LOD 切换需保留证据物体、稳定 ID、门状态、抽屉状态和碰撞连续性。

烘焙遮挡剔除适合固定墙体分隔的房间，但它增加 CPU 查询和数据内存，需要在目标机器上比较。可运动的门不能直接作为静态遮挡物烘焙，否则开门后可能仍错误剔除房内；可选 OcclusionPortal 或经过验证的区域可见性逻辑。[Unity 遮挡剔除的适用条件](https://docs.unity3d.com/6000.3/Documentation/Manual/OcclusionCulling.html)

房屋进一步增多后，可将室内陈设分成 additive 场景或资源块，在接近前异步加载，离开足够远且不再可见后延迟卸载。加载距离大于显示距离，卸载距离再大一些，防止玩家在门口来回走时反复装卸。当前房间和隔窗可见房间优先驻留，正在使用的交互或存档状态先保存到全局数据。是否引入 Addressables，应由实际内存和资源组织需求决定，少量室内可以先使用 SceneManager。

Addressables 能管理依赖和卸载句柄，但不能保证没有激活卡顿；长期设置 activateOnLoad=false 会阻塞后续 AsyncOperation 队列，共用依赖也可能因错误打包重复。若使用，应显式管理加载、取消、激活和释放，检查构建依赖报告。[Addressables 场景加载与依赖](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/LoadingScenes.html)

## 建议的画质档位

这是后续实现方案，当前游戏还没有正式低中高设置菜单。画质档位改变渲染成本，所有档位仍保留同一调查内容、近景重要模型、可进入空间、实体门、透明窗和证物清晰度。

| 控制项 | 低配流畅 | 均衡 | 高画质 |
| --- | --- | --- | --- |
| 三维渲染比例 | 约 0.7–0.85，按显示分辨率调整 | 0.9–1.0 | 原生 1.0，可选更高显示分辨率 |
| UI 和证物阅读 | 保持清晰，独立于三维降分辨率 | 同左 | 同左 |
| 抗锯齿 | FXAA 或 2× MSAA，比较锐度 | 2× MSAA | 4× MSAA，按 GPU 余量调整 |
| SSAO | 关闭或半分辨率低质量 | 半分辨率 | 完整质量，实测成本 |
| 主要实时阴影 | 约 15–25m，1–2 级联，512–1024px | 约 30–40m，2 级联 | 约 45–55m，2–4 级联，2048px |
| 额外灯阴影 | 关闭，保留烘焙氛围 | 附近少量重要灯 | 附近有限配额，避免全镇点灯同时投影 |
| 环境贴图 | 常用 512–1024，重点资源单独保留 | 常用 1024–2048 | 重点资源 2048，确有近景收益才用 4096 |
| 模型分级 | 更早切换，近景重点仍使用完整模型 | 适中切换 | 更远距离保留细节 |
| 反射 | 烘焙或低分辨率探针 | 中等探针质量 | 更高质量探针，有需要时受控刷新 |
| 房屋加载与剔除 | 必须有 | 必须有 | 必须有，可扩大驻留范围 |

画质高的收益来自美术资源、照明、材质和显示精度共同提升。更强的电脑可以把这些效果开得更高，但调节条不会生成缺失的高级模型，也不能解决没有资源卸载造成的长期内存增长。无需为了增加画质档位换到 HDRP；先把现有 URP 内容与档位做好。

正式实现时，需修改构建源中的覆盖逻辑：[BuildSlice.cs](https://github.com/xichengchen1111-hub/game_test/blob/main/game/Assets/Editor/BuildSlice.cs#L399) 每次构建都会写回 HDR、4× MSAA、55m 阴影和 2048 主阴影图。只手改管线资产会被下一次构建覆盖。应保存独立档位资产、用户选择和首次启动的保守默认值，再提供自定义参数。当前程序锁定 60 帧，可根据实际需求另提供 30／60／不限帧选项。

## 贴图和资源制作规范

同一张 RGBA8 贴图在 GPU 中的大小与压缩 PNG 的磁盘大小不同。含完整 mip 链的近似成本如下，不含对齐、驱动和其他资源开销：

| 分辨率 | RGBA8 | 每 4×4 像素 16 字节的块压缩格式 |
| --- | ---: | ---: |
| 1024×1024 | 5.33MiB | 1.33MiB |
| 2048×2048 | 21.33MiB | 5.33MiB |
| 4096×4096 | 85.33MiB | 21.33MiB |

一套全新 4K Base／Normal／Mask 即使都采用该类块压缩，完整 mip 链仍约 64MiB；20 套独特且同时驻留的资源约 1.25GiB，只是算术示例，不是当前游戏用量。复用同一套贴图和 mesh 不会像 20 套独特资源一样增加纹理内存，但仍会增加实例、渲染和可能的合批缓冲成本。

保存高质量可编辑母版，运行时按用途导入。常用木材、墙面、金属和布料复用材质，局部纹理控制密度；不要让每颗螺丝、每条表链都成为单独渲染组件。柜台可以按柜组分块，透明层、抽屉和门保持独立，避免把可动部分合入静态批次。近景检查用的精细钟表可以在检查界面单独加载，世界中的同款用较轻版本，时间与证据仍读同一数据。

启用贴图 mip 串流需要质量设置和各贴图导入设置同时配置；不能只打开一个总开关。脚本生成 mesh 的 UV 密度也需正确计算，UI 及特定贴图应单独验证清晰度。[Unity mip 串流设置](https://docs.unity3d.com/6000.3/Documentation/Manual/TextureStreaming-use.html)

## 低配目标与验证顺序

最低设备尚未指定具体型号。建议用一台 8GB 内存、UHD 620／630 一类旧核显 Windows 笔记本作为保底测试设备，再用一台常见较新核显或入门独显电脑验证 60 帧目标。不同核显、单双通道内存、供电和散热差异很大，目前不能给这些设备承诺帧率。

建议先设“弱设备 720p 稳定 30 帧保底、较新入门设备争取 60 帧”的验收目标。30 帧整帧预算为 33.33ms，60 帧为 16.67ms；设计时为瞬时加载和波动留出约 20% 余量。CPU 与 GPU 可以并行，不能把两者耗时简单相加得到整帧时间。目标可根据实际低配设备结果上调，不能用开发电脑测速直接换算。

作为首轮制作约束，可以先把低档常见视角的绘制调用控制在约 300–500、包含额外 pass 的提交三角面约 30–60 万，并为重点物体设置例外；这只是便于发现增长的初始预算，不是任何核显必然达标的安全线。进程常驻内存可先以约 1.5GiB、流式纹理约 256MiB 为初始检查值，同时测实际图形资源、共享内存和系统余量；纹理预算并不约束全部显存。

实施顺序建议如下：

1. **继续扩大内容前**：建立独立低中高档资产；修正构建覆盖；优先减少额外实时阴影与昂贵屏幕效果；保存当前基线，以同一场景比较。检查 720p 与 1080p 的中文、钟面和票据可读性。
2. **制作下一批房屋时**：资产同时交付近中远模型、共用材质、简单碰撞和可见性分组；至少做一组多房屋同时可见的真实关卡，验证分级、窗外看内、内看外和开门时不会突然消失。房屋数量只是触发复核的里程碑，不能作为统一性能上限。
3. **常驻内存明显增长后**：按区域异步加载和延迟卸载，检查重复依赖；先预加载可见房屋，保证旧存档和门窗状态可恢复。不要每过门口调用一次全局 UnloadUnusedAssets 或强制 GC。
4. **每个内容里程碑**：在真实低配与开发电脑测 release 包，记录 GPU、主线程、绘制调用、内存、P95／P99 和超过 50／100ms 的帧；单独测试冷启动第一次进入、重复进出、快速转身看多窗、同时开门、查看证据、读档和 20–30 分钟连续探索。帧数上限与电源模式固定，首次运行与暖缓存结果分开。

本次只测了当前内容，没有复制多座店铺做容量推断，也没有在低配、Mac、HDD 或完整全镇上测量。后续容量要由真实内容最重视角和目标设备决定。优先落实光影分档、资产 LOD 和房屋可见性，可以继续提高近景美术质量，同时控制扩展成本。
